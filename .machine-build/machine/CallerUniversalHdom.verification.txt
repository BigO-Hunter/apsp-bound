THE VERDICT — `hdom` CLOSES; ONE class-(iii) NAME REMAINS, AND IT IS THE HONEST
MINIMUM. `hdom` as stated (a `completeCost` domination of the COMPOSITE) is now a
theorem. What it still costs is a bound on `cacheTime`, and that is NOT derivable
in this tree: `Light.Solves` bounds a run ABOVE by its claimed clock ("ends within
T steps"), so a larger `Tn` is a weaker claim that is still true, and nothing
bounds the cache solver's clock from above. `univTn` carries `cacheTime (n²) U` as
a FREE argument; for an adversarial clock (`λ n U, (n+U)^1000`)
`CallerHdom (univTn cacheTime)` is simply FALSE. So the remaining name is:

  the CACHE SOLVER'S CLOCK BUDGET —
  `univCallB + cacheTime (n²) U ≤ (2·log₂U + 6)·(770·n²)`, all `n ≥ 1`, all `U`.

DISCLOSED, because it is easy to over-claim the other way: this is NOT a weaker
premise than `hdom`. It is uniform in `U` where `hdom` takes a sup over `U ≤ n^κ`,
so it is STRONGER. What it buys is justifiability, not strength: the party that
lands the cache boundary (`Solves cacheTask …`) is the party that knows its own
clock, whereas `hdom` was a domination statement about a composite whose largest
term belongs to that other party. The SLOT changes owner; the COUNT does not.

A FALSE LEMMA WAS CAUGHT BY THE MACHINE, and is recorded rather than swept away.
An earlier draft of this module carried `hcT_of_cacheClock`, asserting that the
"pure" clock bound `cacheTime (n²) U ≤ (2log₂U+6)(770n²)` implies the bundled form
above. It does not: `18 + c ≤ A` does not follow from `c ≤ A`. `omega` produced the
counterexample (`c = A`, `univCallB = 18`) on the first elaboration. The lemma is
deleted and the module header says so, so the next mind does not re-derive it.

BUILD ENVIRONMENT — four measured obstacles, because they cost this pass hours and
will cost the next mind the same if not named.

 1. THE BENCH LOCK IS A WALL, NOT A QUEUE. `/Volumes/Substrate-1/bigo/.build.lock`
    (taken by `_build_lock.py`) was held continuously by a peer lane for 2 h; a
    waiter of ours sat 6+ min with 0:00.12 CPU and no children — blocked, which in
    a log reads exactly like "still elaborating". A non-blocking `flock` probe is
    the only honest test of whether the lock is HELD or your build is RUNNING.
 2. THE REAPER KILLS ON SWAP GROWTH, and it kills `lean`/`lake` by cmdline regex
    `/(lean|lake)\b`. Receipts for this module: killed at free_gb 5.05, 4.49, 0.14,
    3.15, 5.65, 7.73, 0.61 — FIVE of seven above the 3.0 GB floor, with ~1.2 GB of
    unused swap. So it was the growth arm every time, not the floor.
 3. THAT REGEX MATCHES YOUR WRAPPER TOO. `-o .lake/build/lib/lean/X.olean` puts
    `/lean` in the wrapper's own cmdline, so the reaper TERMs the wrapper (receipts:
    31 MB RSS, not the compiler) and the tool call reads `Killed by SIGTERM`. Build
    from a FILE, and write the olean outside the `/lean` tree.
 4. `-M` IS LOAD-BEARING AND 4000 IS TOO SMALL. `-M4000` does not protect the box;
    it ABORTS lean at 4 GB (`lean::memory_exception: excessive memory consumption
    detected at 'interpreter'`, rc=134 at ~35 s). `-M6000` completes the module in
    43-54 s. A build attempted without a cap inherits whatever the box has.

  The shape that worked: `lean` invoked directly with `LEAN_PATH` from `lake env`
  (no `lake build`, no lock), output to `/private/tmp/hdom_olean/`, started the
  instant a reaper pass had just landed (passes are ~85-90 s apart, so the window
  is the whole gap between them). Nothing in the shared `.lake` is written, so the
  race the lock exists to prevent cannot occur.
